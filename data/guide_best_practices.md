# הרגלי עבודה טובים בתחזוקת פרויקט בגיטהב

קובץ זה מרכז כללים מעשיים לתחזוקה מסודרת של פרויקט לאורך זמן.

## commits קטנים ותכופים

עדיף לבצע commit אחרי כל שינוי הגיוני אחד (תיקון תקלה, הוספת פונקציה), ולא commit אחד גדול בסוף יום עבודה. היתרונות:
- קל להבין מה כל commit עשה
- קל לבטל שינוי אחד בלי לבטל את כל השאר
- קל למצוא מתי נכנסה תקלה

## הודעות commit ברורות

הודעה טובה מסבירה **מה** השתנה, בקצרה ובבירור.

דוגמאות טובות:
```
תיקון שגיאה בשמירת טופס הרשמה
הוספת בדיקה לאורך הסיסמה
עדכון הוראות התקנה ב-README
```

דוגמאות לא טובות:
```
שינויים
תיקון
asdf
```

מקובל לכתוב את ההודעה בלשון ציווי או תיאור קצר, עד כ-50 תווים בשורה הראשונה. אם צריך פירוט, משאירים שורה ריקה וכותבים הסבר בהמשך.

## למשוך לפני שעובדים, להעלות כשמסיימים

- **בתחילת עבודה:** `git pull`, כדי לעבוד על הגרסה העדכנית.
- **בסיום עבודה:** `git push`, כדי שהעבודה תישמר בגיטהב ותהיה זמינה לאחרים ובמחשבים אחרים.

ההרגל הזה לבדו מונע את רוב הקונפליקטים.

## לעבוד בענפים

גם כשעובדים לבד, כדאי לפתח תכונות חדשות בענף נפרד ולמזג ל-`main` רק כשהן עובדות. כך `main` תמיד מכיל גרסה תקינה. ראה בקובץ ענפים ו-Pull Requests.

## קובץ .gitignore מההתחלה

ליצור `.gitignore` לפני ה-commit הראשון, כדי שקבצים מיותרים לא ייכנסו להיסטוריה. דברים שבדרך כלל לא מעלים:
- תיקיות של ספריות שמותקנות אוטומטית (`node_modules/`, `venv/`)
- קבצים שנוצרים בהרצה או בבנייה (`__pycache__/`, `build/`, `dist/`)
- קבצי הגדרות של עורך הקוד ושל מערכת ההפעלה (`.vscode/`, `.DS_Store`, `Thumbs.db`)
- קבצי סודות (`.env`)

GitHub מציע תבניות מוכנות של `.gitignore` לפי שפה, בעת יצירת מאגר חדש, או במאגר `github/gitignore`.

## קובץ רשימת ספריות

כדי שאחרים יוכלו להריץ את הפרויקט, שמור במאגר רשימה של הספריות שהוא צריך, במקום להעלות את הספריות עצמן:
- Python: `requirements.txt` (אפשר ליצור עם `pip freeze > requirements.txt`)
- Node.js: `package.json` (נוצר עם `npm init`)

## לשמור על README מעודכן

בכל פעם שמשתנה אופן ההתקנה או ההרצה, לעדכן את ה-README באותו commit. README שגוי גרוע מ-README חסר.

## לא לשנות היסטוריה שכבר הועלתה

פקודות שמשנות היסטוריה, כמו `git commit --amend`, `git reset` ו-`git rebase`, בטוחות רק לפני push. אחרי שהשינויים כבר בגיטהב (ובמיוחד בענף משותף), לבטל שינוי עם `git revert`, שיוצר commit חדש ולא מוחק היסטוריה. ובשום מקרה לא `git push --force` על ענף משותף.

## לנקות ענפים שמוזגו

אחרי שענף מוזג, למחוק אותו גם בגיטהב וגם במחשב, כדי שרשימת הענפים תישאר קריאה. ראה בקובץ הגדרות מאגר.

## לסמן גרסאות

כשהפרויקט מגיע לנקודה יציבה (למשל הגשה), ליצור תגית ו-Release. כך תמיד אפשר לחזור לגרסה הזו בדיוק. ראה בקובץ גרסאות ו-Releases.

## רשימת בדיקה לפני push

1. `git status`: אין קבצים רגישים או מיותרים ברשימה
2. הקוד רץ והבדיקות עוברות
3. הודעת ה-commit ברורה
4. אם צריך, ה-README עודכן
5. `git pull` לפני `git push`, אם עובדים עם אחרים
